| 対象 | 項目 | 判定 | 確認結果 |

## 2. 要求分析・レビュー項目

対象成果物: `03_usecase_diagram.puml`, `04_usecase_description.md`, `05`〜`07`（アクティビティ図）

| 対象 | 項目 | 判定 | 確認結果 |
|---|---|---|---|
| 全体 | 要求される機能、関係するアクタを網羅している | ○ | 課題要求（3つ以上）に対し5ユースケース、アクタは利用者・フロント係の2種 |
| 全体 | 抽象的な機能要求の記述ではなく、具体的な振る舞いの記述となっている | ○ | 全5UCについて基本フローを番号付きステップで記述し、アクティビティ図（UC1・UC2・UC3）で分岐と終了条件を可視化した |
| 全体 | 配置や色、フォントなどが読みやすい | ○ | ユースケース図は `left to right direction` でアクタとUCを左右に分離。アクティビティ図はスイムレーンで役割を分離 |
| ユースケース | 各ユースケースはまとまった振る舞いの単位である | ○ | いずれもアクタにとって価値のある一連の処理（予約の完了、チェックインの完了など）で区切った |
| ユースケース | 現在時制かつ能動態の動詞句としてユースケース名がつけられている | ○ | 「部屋を予約する」「チェックインする」「予約をキャンセルする」等、すべて現在時制の能動態 |
| ユースケース | 全てのユースケースの抽象度はおおむね同程度である | ○ | 5つすべてが「1回の窓口対応で完結する処理」の粒度。UC4のみ他UCからincludeされる共通機能だが、単独でも利用者が使える単位である |
| アクタ | 関わるユースケースとのみ関係づけられている | △ | 図では利用者→UC1/UC2/UC4/UC5、フロント係→UC2/UC3。一方でUC4の記述のアクタは「利用者、フロント係」であり、**図にフロント係→UC4の関連線がない**。フロント係はUC2経由（include）でUC4を使うという解釈だが、記述と図で読み取れるアクタが一致しない |
| ユースケース記述 | 必要な事前条件、事後条件、基本系列、代替・例外系列を明確かつ簡潔に記述している | ○ | 全5UCで5項目すべてを記述。代替系列は正常系の分岐、例外系列は異常事象への対応として分けた |
| ユースケース記述 | システムへの入力に加えて、システムからの応答を明記している | ○ | アクタの入力ステップの直後にシステムの応答ステップを置いた（例: UC1「1. 利用者が宿泊日・客室タイプを指定する」→「2. システムが該当する空室一覧を提示する」） |
| ユースケース記述 | 各ステップは現在時制と能動句で記述されている | ○ | 全ステップを「〜が〜する」の能動句で統一 |

## 3. システム分析・レビュー項目

対象成果物: `08_bce_objects.md`, `08a`〜`08e`（コラボレーション図）, `09_system_class_diagram.puml`

| 対象 | 項目 | 判定 | 確認結果 |
|---|---|---|---|
| 全体 | ユースケースが要求する全ての振る舞いを網羅している | ○ | UC1〜UC5それぞれにコラボレーション図（08a〜08e）を作成 |
| 全体 | 必要なデータとその置きどころが明確化されている | ○ | `08_bce_objects.md` に「データの置きどころ」の表を作成。宿泊日→Reservation、単価→RoomRate 等を明示 |
| 全体 | コラボレーション図における相互作用や可能なオブジェクト数が、クラス図の関係・操作・多重度と対応している | ○ | コラボレーション図のメッセージ名を09の操作名と一対一に対応させ、オブジェクト数を09の多重度に一致させた（例: Reservation 1件に対し ServiceUsage 0..*） |
| オブジェクト | バウンダリ、コントロール、エンティティの3つ組が、それぞれ当該種別の役割に合致して識別されている | ○ | 識別方針を `08_bce_objects.md` に明文化（バウンダリは入出力のみ、コントロールは手順制御、エンティティはデータ保持と自身の状態変更のみ） |

| 相互作用 | ユースケースの基本系列に加えて、代替・例外系列も描かれている | ○ | ガード条件と分岐番号（1, 1.1, 2a…）で代替・例外系列を同一図内に表現 |
| 相互作用 | 描かれた相互作用とその順序が、対応するユースケース記述に合致している | ○ | メッセージ番号を呼び出し階層の入れ子番号とし、ユースケース記述のステップ順と対応させた |
| 相互作用 | バウンダリ、コントロール、エンティティ間で書いてよい相互作用のみが書かれている | ○ | 許される組み合わせ（アクタ↔バウンダリ、バウンダリ↔コントロール、コントロール↔コントロール、コントロール↔エンティティ）を `08_bce_objects.md` に規律として明記し、それ以外は描いていない |

## 4. アーキテクチャ設計・レビュー項目

対象成果物: `10_package_diagram.puml`, `10_architecture_design.md`, `09_system_class_diagram.puml`

| 対象 | 項目 | 判定 | 確認結果 |
|---|---|---|---|
| アーキテクチャ | 適切なパターンや実現手段の選択により、全ての非機能要求を満足している | ○ | 多層アーキテクチャを採用。非機能要求7項目それぞれの実現手段と根拠を `10_architecture_design.md` 第2節の表に整理した |
| アーキテクチャ | 実装上の制約を満足している | △ | 「Java言語・JavaVM環境、**または他言語**」「テキストUIが基本、**発展形も可**」の許容に基づき Python + FastAPI + React を採用した。一方で「提供される部分実装に従うこと」については、**Javaの半完成コードを使わず一から実装した**ため従っていない。型検査（mypy strict）とCIで品質を担保する方針で代替している |
| アーキテクチャ | 「良い設計のための基本技術」を的確に用いている | ○ | 抽象化・モジュール化・関心事の分離・情報隠蔽・機能独立性（高凝集低結合）の適用箇所を `10_architecture_design.md` 第3節に対応づけた |
| アーキテクチャ | パッケージ設計原則を満足している | △ | 6原則のうち ADP・SDP・REP は満たす。CRP・CCP・SAP は部分的（ユースケース追加が2パッケージに及ぶ、ドメイン層が具象中心で抽象度が低い）。詳細と改善方針は `10_architecture_design.md` 第4節 |
| アーキテクチャ | 配置や色、フォントなどが読みやすい | ○ | 層ごとに背景色を分け、依存の矢印を層間に集約して交差を減らした。安定／不安定の勾配を注釈で示した |
| クラス | 求められる全機能を満足するように操作および属性の割り当てが確定している | ○ | 09で全エンティティの属性と操作を確定。操作はコラボレーション図のメッセージと一対一 |
| クラス | 実装可能な形で表現されている（型、名前など） | ○ | 属性・操作に型（String, Date, Money, boolean, ReservationStatus 等）を明記。実装のクラス名・メソッド名と一致している |
| クラス間関係 | 全てについて方向（誘導可能性）が明示されている | △ | エンティティ間の関連は無方向の関連（`--`）で描いており、**誘導可能性の矢印を付けていない**。実装では Reservation から Guest・Room を辿る一方向であり、これを矢印で明示すべき |
| クラス間関係 | 全てについて多重度が明示されている | ○ | エンティティ間の全関連に多重度を明示（依存関係 `..>` は多重度の対象外） |
| クラス間関係 | 必要な集約、合成集約（コンポジション）の関係が明示されている | △ | 09に集約・合成集約を用いていない。`Reservation`—`Charge`（0..1）と `Reservation`—`ServiceUsage`（0..*）は予約に従属し予約なしでは存在しないため、**合成集約で表すのが適切** |

## 5. 実装・レビュー項目（抜粋）

対象成果物: `apps/backend`, `apps/frontend`

| 対象 | 項目 | 判定 | 確認結果 |
|---|---|---|---|
| 全体 | 設計モデルに適合する形で、構造、振る舞い、関連、相互作用が実装されている | ○ | 09のBCE分類が層に、クラス名がモジュール／クラス名に対応。対応表は `10_architecture_design.md` 第5節 |
| 全体 | 必要に応じて再利用が行われている | ○ | UC4（予約内容の確認）をUC2・UC5からinclude。FastAPI・SQLAlchemy・Pydantic・sqlc等の既存資産を利用し、DTO変換は `from_domain` に共通化 |
| 全体 | 意図が分かりやすく実装されている | ○ | 各モジュール冒頭のdocstringに対応するUC番号とBCE種別、設計意図（トランザクション境界をどこに置くか等）を日本語で記載 |
| 全体 | 全ての機能が実装されている | ○ | UC1〜UC5すべてと、予約前の部屋タイプ閲覧をAPI・画面の両方で実装。動作はヘッドレスブラウザで確認済み |
| 要素 | 全ての属性・変数・引数が適切に初期化・代入されている | ○ | エンティティは `frozen dataclass` で生成時に全属性を確定。未初期化・部分初期化は mypy strict が検出する |
| 要素 | 各メソッドの大きさと複雑さは適切に抑えられている | ○ | 各Controlは1ユースケース1メソッドで、最長の `CheckOutControl.check_out()` でも約30行。料金計算はドメイン層に委譲して分岐を持たせていない |
| 要素 | 命名は分かりやすく一貫している | ○ | 09のクラス名と実装のクラス名を一致させた（`CheckInControl`, `Reservation.check_in()` 等）。ruff の import 順・整形規則をCIで強制 |
| 要素 | ループ制御の判定が正しい | ○ | 明示的なループは料金合計（`sum` による内包表記）とDTO変換のみで、境界条件を持つ手続き的ループを書いていない |
| 要素 | 条件分岐の判定が正しい | ○ | 状態遷移の可否判定（チェックイン・チェックアウト・キャンセル）について、許される遷移と許されない遷移の両方をユニットテストで網羅（24ケース、`packages/libs/tests/domain/`） |
| 要素 | 扱う事柄に特化した例外を適切に用いている | ○ | `ReservationNotFound` / `InvalidReservationState` / `InvalidReservationPeriod` / `NoAvailableRoom` / `RoomRateNotConfigured` を定義し、UI層で個別のHTTPステータスへ変換している |

## 7. 確認により判明した課題（△の項目）

| # | 課題 | 対応方針 | 工数感 |
|---|---|---|---|
| 1 | ドメインクラス図に属性がなく、用語辞書として粗い | 主要クラスに属性を追記する | 小 |
| 2 | ドメインオブジェクト図が具体値を持たず「具体的な状況」になっていない | インスタンス名と属性値を入れる | 小 |
| 3 | ホテル—客室が単純関連（集約が自然） | 集約に変更する | 小 |
| 4 | ユースケース図にフロント係→UC4の関連線がなく、UC4の記述と一致しない | 図に線を追加するか、記述側のアクタを利用者のみに絞る | 小 |
| 5 | 09のエンティティ間関連に誘導可能性の矢印がない | 実装の参照方向に合わせて矢印を付ける | 小 |
| 6 | 09に合成集約がない（Reservation—Charge / ServiceUsage） | 合成集約に変更する | 小 |
| 7 | パッケージ設計原則 CRP・CCP・SAP が部分的 | Repository を `Protocol` で抽象化すればSAPと依存性逆転が明確になる。CCPは層分離とのトレードオフとして受容 | 中 |
| 8 | 実装上の制約「提供される部分実装に従うこと」に従っていない | 「または他言語」の許容に基づく判断としてレポートに明記する | — |
| 9 | アプリケーション層（コントロール）のテストがない | 実DBを使う統合テストジョブの追加、またはRepositoryのDI化が必要 | 中 |
